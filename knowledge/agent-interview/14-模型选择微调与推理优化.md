# 模型选择、微调与推理优化

同义词：Model Selection、模型选型、SFT、Supervised Fine-Tuning、监督微调、PEFT、LoRA、Preference Optimization、偏好优化、Distillation、蒸馏、Quantization、量化、Inference Optimization、推理优化。本文是通用技术资料。

## 一句话结论

模型选择应在真实任务集上权衡质量、工具能力、延迟、成本、隐私和运维。Prompt 解决任务指令，RAG 提供可更新事实，微调改变稳定行为与能力分布；三者不是互相替代，应先建立基线和评测再增加训练成本。

## 模型选型的评估维度

质量包括领域正确性、指令遵循、结构化输出、工具选择、多语言和长 Context 下的稳定性。系统指标包括首 Token、输出速率、P95 端到端延迟、限流、可用性和费用。治理还包括数据传输、保留、区域、版本固定和供应商锁定。

公开 Benchmark 只用于初筛，不能代替产品题集。在相同 Prompt、工具、数据和评分规则下对比，保留失败分类和置信区间，而不只比一个平均分。

## Prompt、RAG 还是微调

**Prompt** 适合快速定义任务、格式、约束和 Few-shot 示例。如果问题是缺少最新或私有事实，增加 Prompt 或微调都不如检索可追溯证据。

**RAG** 适合频繁更新、需要引用、按用户授权查询的知识。它的主要失败面是解析、召回、重排和证据使用，不是训练模型。

**微调** 适合大量、稳定、可示范的行为模式，例如领域风格、特定格式、分类边界或工具调用习惯。它不是存储经常变化事实的好方法，也不能替代权限与外部验证。

### 什么时候真的需要微调

在强基线 Prompt 和 RAG 之后，某类稳定行为仍经常失败，有足够高质量、合法且代表真实分布的训练数据，并能定义离线与线上成功指标时，才值得。微调前要证明收益可能大于数据、训练、部署和持续回归成本。

## SFT 与训练数据

SFT 使用输入-目标输出样本继续训练模型。数据中的格式、偏见、错误事实和过长答案都会被学习，所以数据质量、覆盖和评审通常比简单增加数量更重要。

训练集、验证集和最终保留评测集按来源或时间切分，防止近重复和同一会话泄漏。保留困难、拒绝、无答案和安全样例，不要只有正常成功答案。

## PEFT 与 LoRA

PEFT 只训练少量新增或选定参数，降低训练显存、存储和多任务适配器管理成本。LoRA 将权重更新表示为低秩分解，冻结原权重并训练小矩阵。

参数高效不代表数据或评测要求降低。Adapter 与基座模型版本必须绑定，合并或动态加载后重新检查质量、延迟与并发。

## 偏好优化

偏好数据表示在给定输入下哪个回答更好。不同方法可以用奖励模型与强化学习，或使用直接偏好目标优化。但偏好优化学到的是标注规则和数据分布，不保证外部事实或工具安全。

偏好数据要明确 Rubric，处理评审者分歧、长度偏好、风格偏好和顺序偏差。如果把“更自信”错误标为“更正确”，训练可能放大幻觉。

## 蒸馏

蒸馏让小模型学习教师模型的输出分布、中间信号或合成示例，目标是在受限任务上获得较低延迟和成本。教师错误、风格和偏见也会被继承，所以合成数据需要去重、过滤和独立标签。

蒸馏不保证小模型在分布外复制教师。适合边界清晰、数据量大和验证可编程的子任务，例如分类、信息抽取或特定路由，不是默认替代复杂 Agent 规划。

## 量化与推理优化

### 量化一定会让模型更快吗

不一定。量化减少权重体积和内存带宽，但真实速度还取决于硬件是否有高效低位算子、是否需要频繁反量化、批处理、KV Cache 与调度。必须在目标硬件和 Agent 任务上同时测吞吐、P95 和质量。

量化用较低位宽表示权重，也可涉及激活或 KV Cache，以降低内存带宽和存储，并可能提高吞吐。质量损失取决于模型、位宽、校准数据、算子与任务，不能只看通用困惑度。

其他手段包括连续批处理、请求调度、前缀缓存、推测解码、模型并行和高效注意力算子。它们在吞吐、首 Token、单请求延迟和显存之间有不同取舍，必须按目标流量实测。

## 自托管还是 API

API 减少模型服务、弹性和硬件运维，但带来网络、供应商限额、数据管理和版本变化问题。自托管可控制模型、数据边界和容量，但需要 GPU 规划、推理引擎、监控、升级、安全和值班能力。

用负载的稳定性、数据要求、总拥有成本和内部运维能力决定，不能只比 GPU 小时与 API Token 单价。混合方案要验证不同模型的格式、工具与安全行为兼容性。

## 常见失败场景

- 看公开排行榜直接选模型，没有工具和业务题集。
- 用微调记忆频繁更新政策，无法及时删除或引用。
- 训练和评测包含近重复对话，分数虚高。
- 偏好标注奖励长且自信的回答，幻觉反而增加。
- 量化只测通用指标，工具参数、数字和多语言任务退化未发现。
- 只比 Token 单价，忽略低成功率导致的重试和人工成本。

## 生产实现检查表

用内部任务集对比模型；记录质量、P95、成功任务成本与治理约束；先做 Prompt 和 RAG 基线；微调有明确稳定行为目标；数据合法、去重、分层且有保留集；Adapter 绑定基座版本；蒸馏与偏好数据独立评审；量化用目标 Agent 任务回归；自托管包含完整运维成本；发布有 Canary 与回滚。

## 20 秒口述

模型选型我会用真实任务集比较正确性、工具能力、P95、每成功任务成本和数据要求。Prompt 负责任务指令，RAG 提供可更新事实，微调适合大量稳定行为。只有基线仍有明确可测失败且数据足够时，我才增加微调。

## 1 至 2 分钟展开

我首先建立包含正常、困难、工具故障和安全案例的内部评测集，在相同系统条件下比较候选模型的成功率、延迟、成本和数据约束。如果缺最新事实，优先 RAG；如果是任务和格式，先优化 Prompt；如果是大量稳定且可示范的行为模式，才考虑 SFT 或 PEFT。训练数据按来源去重和切分，保留独立测试。部署时再评估蒸馏、量化或模型路由，但所有优化都回到相同 Agent 题集验证。

## 高频追问

### RAG 和微调怎么选

问题是“模型不知道哪些当前事实”时用 RAG，因为可更新、可授权、可引用。问题是“在大量类似输入上怎样稳定行为”时考虑微调。实际系统可同时使用，但必须分别评测检索与行为。

### LoRA 为什么更省资源

它冻结大部分基座权重，只学习低秩更新矩阵，因此需保存的可训练参数和优化器状态更少。但激活、数据、评测和基座模型推理成本仍存在，不能把“参数少”等同于“总成本很低”。

## 系统设计练习

为工单 Agent 选模型：用真实脱敏题集分别评估意图分类、信息抽取、政策 RAG 问答和工具调用；小模型处理高频分类，低置信度路由大模型；政策始终用 RAG 而不训入参数；只对稳定抽取格式考虑 PEFT；上线按每成功工单成本和错路由率验证。
