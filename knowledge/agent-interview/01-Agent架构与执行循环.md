# Agent 架构与执行循环

同义词：AI Agent、智能体、Agent Loop、Observe-Plan-Act、Agentic Workflow、编排器、Orchestrator、状态机。本文是通用技术资料，不证明候选人实现过这些机制。

## 一句话结论

Agent 不是“能聊天的模型”，而是一个围绕目标持续读取状态、选择动作、调用外部能力并根据结果调整后续行为的任务系统。生产级 Agent 的关键不在于让模型拥有最大自由，而在于明确模型、确定性代码、工具、状态存储和人工分别控制什么。

## Agent、Chatbot 与 Workflow 的边界

Chatbot 的主要输出是文本回复；Workflow 的步骤和分支主要由代码预先确定；Agent 则允许模型根据当前状态动态决定一个或多个后续动作。三者可以组合：聊天界面接收目标，Workflow 管理阶段和权限，Agent 在局部阶段完成语义判断或工具选择。

判断标准不是“是否调用 LLM”，而是谁拥有控制流。代码固定执行“检索后生成”仍是 Workflow；模型根据观察结果决定继续搜索、换工具还是澄清，才具有 Agent 特征。自治程度越高，测试空间、成本和风险通常越大。

### Agent 和普通 Workflow 到底有什么区别

普通 Workflow 的主要步骤和分支由代码预先编排；Agent 允许模型根据实时 Observation 选择下一动作、更换工具、重规划或澄清。两者不对立，生产系统常用 Workflow 固定权限、阶段和验收，只在路径无法预先枚举的局部引入 Agent。

## 核心组件

一个最小 Agent 包括目标、模型、工具、状态和控制器。目标定义成功标准；模型负责语义判断和动作建议；工具连接数据库、搜索、代码执行或业务 API；状态保存消息、计划、工具结果和预算；控制器验证动作、执行工具、更新状态并决定继续或停止。

模型输出应被视为建议而不是系统事实。真正的权限检查、参数校验、事务边界、预算扣减和终止判定应由控制器执行。否则 Prompt 中的一句话就可能绕过安全边界。

## Observe-Plan-Act 执行循环

一次循环可以表示为：读取目标与状态；构造受预算限制的 Context；让模型选择下一动作；解析并校验结构化动作；执行工具；把结果作为 Observation 写回状态；检查成功、失败、等待、澄清或继续。

Observation 必须描述可验证事实，例如 HTTP 状态、数据库记录版本或测试结果，而不是只有“操作成功”。控制器还应记录步骤号、模型和 Prompt 版本、工具参数摘要、耗时、费用及错误类型，支持线上追踪和离线重放。

## 确定性边界与自治范围

适合代码控制的内容包括权限、金额上限、必经审批、状态转换、最大重试和完成条件。适合模型判断的内容包括用户意图、模糊任务拆分、非结构化信息提取、候选工具选择和自然语言总结。

如果任务可以用有限状态机可靠表达，应优先固定流程。只有当步骤无法预先枚举，且工具结果会改变后续策略时，才增加自治循环。常见折中是“外层状态机加内层 Agent”：代码控制阶段，模型只在某一阶段内探索。

### 哪些事情不能交给大模型决定

权限授予、合规规则、金额和资源上限、不可逆状态转换、租户隔离、凭据访问以及任务是否真实完成，不能只由模型决定。这些约束由代码、策略服务或权威系统强制；模型可以解释规则或提出建议，但不能绕过控制器。

## 状态模型与检查点

状态至少应区分不可变输入、当前计划、已执行动作、工具观察、预算、权限和最终产物。消息历史只是状态的一部分，不能替代业务状态。例如“已发送邮件”应由邮件系统的消息 ID 证明，而不是由 assistant 消息证明。

长任务需要检查点。检查点应在外部副作用后持久化，并保存幂等键或结果标识；恢复时先读取权威系统状态，再决定跳过、重试或补偿。仅恢复模型对话可能重复执行已发生的操作。

## 终止条件与进展检测

终止至少包含成功、不可恢复失败、需要用户输入、需要人工审批、预算耗尽和用户取消六类状态。成功应绑定任务特定条件，例如文件存在且测试通过、工单状态为已创建，而不是模型输出 `done=true` 就结束。

防止死循环需要最大步骤、墙钟时间、Token、费用和工具调用预算，并检测连续相同工具、相同参数、相同错误或状态摘要不变。没有进展时应换策略、请求澄清或安全停止，而不是盲目增加重试次数。

## Human-in-the-loop

人工介入不只是一枚“确认按钮”。触发点包括高风险副作用、权限提升、不可逆操作、信息缺失、多种方案代价差异显著，以及 Agent 置信不足。确认界面应展示将执行的具体动作、目标、关键参数和影响，不要求用户批准一段模糊的思考过程。

人工修改计划后，需要生成新的状态版本并使旧动作失效。否则后台仍可能按旧计划继续。取消等待也不等于撤销已经发生的外部副作用。

## 常见失败场景

- 把模型的自然语言声明当作完成证据，实际工具没有执行。
- 工具成功后进程崩溃，恢复时重复执行副作用。
- Observation 包含网页恶意指令，模型把它当作系统指令。
- 所有历史原样塞入 Context，噪声逐轮放大并超过窗口。
- 只设置最大步骤，没有检测重复动作，浪费预算后才停止。
- 自治循环覆盖本可固定的业务流程，导致测试空间不可控。

## 生产实现检查表

先定义状态枚举和任务成功条件；再建立工具注册表与风险等级；控制器统一执行 Schema、权限和预算校验；每一步持久化 Trace；副作用使用幂等键；长任务设置检查点；取消信号贯穿模型和工具；高风险动作走人工审批；最终用权威状态验证结果。

## 20 秒口述

我把 Agent 看成有状态的任务执行系统，而不是一个 Prompt。模型负责语义判断和下一动作建议，控制器负责权限、校验、工具执行、预算和终止。生产中我会用确定性工作流限定边界，只在步骤无法预先枚举的位置引入自治循环，并通过检查点、幂等和外部验证保证可恢复性。

## 1 至 2 分钟展开

设计时我先定义目标、成功条件和风险边界，再建立状态模型。每轮由控制器整理 Context，模型返回结构化动作；控制器校验工具、参数、权限和预算后执行，把真实结果作为 Observation 写回。任务成功必须由外部状态或规则验证。对于长任务，我会在副作用后保存检查点和幂等信息；如果连续动作没有推进状态，就重规划、澄清或停止。这样模型仍有处理非结构化问题的弹性，但不会控制安全边界。

## 高频追问

### Agent 一定比 Workflow 好吗

不是。确定流程更容易测试、解释和控制。只有任务路径依赖非结构化信息、无法提前枚举或需要根据观察动态调整时，Agent 才可能带来收益；否则自治只会增加延迟、成本和失败空间。

### 怎样证明 Agent 完成了任务

使用任务特定验证器读取权威状态，例如测试进程退出码、数据库记录、对象存储文件哈希或第三方 API 返回的资源 ID。模型自评只能作为辅助信号，不能替代验证器。

### 如何设计可恢复的 Agent

持久化版本化状态和步骤结果；对副作用使用幂等键；在恢复时查询权威系统而不是只重放对话；区分可重试、需补偿和需人工处理的失败。检查点与外部动作之间仍可能有竞态，需要用业务事务、Outbox 或外部幂等能力缩小窗口。

### 服务挂了以后怎么恢复 Agent 任务

从最后一个已提交的版本化检查点恢复，再查询外部权威系统确认已发出副作用的真实状态。已成功步骤保留，明确未执行步骤可重试，结果未知则用幂等键查询、补偿或转人工，不盲目重放整段对话。

## 系统设计练习

设计一个 Coding Agent 时，可让代码控制仓库权限、工作区、测试命令和提交边界；模型负责理解需求、定位文件和生成补丁；工具负责搜索、编辑和测试；状态保存变更、测试结果和预算；成功条件是指定测试通过且差异满足范围约束。写入仓库、删除文件和推送远端应按风险单独审批。
