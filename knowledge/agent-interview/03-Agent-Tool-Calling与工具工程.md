# Agent Tool Calling 与工具工程

同义词：Function Calling、函数调用、Tool Use、工具使用、Structured Output、结构化输出、JSON Schema、幂等、副作用、Sandbox。本文是通用技术资料，不证明候选人实现过这些机制。

## 一句话结论

Tool Calling 是让模型提出结构化工具请求，而不是把执行权限直接交给模型。应用负责提供工具、校验参数、检查权限、执行调用、处理副作用，并把受控结果反馈给模型；模型选择了工具不等于工具应当被执行。

## 完整调用链路

典型链路是：应用把工具名称、描述和参数 Schema 提供给模型；模型返回工具名与参数；控制器解析并校验；权限层判断能否执行；工具适配器调用外部系统；结果被裁剪、标记来源后作为 Observation 返回；模型决定回答、继续调用或请求澄清。

工具执行应产生稳定的调用 ID，Trace 记录参数摘要、调用方、目标、耗时、结果和错误。敏感字段需要脱敏，原始凭据不能进入模型上下文或普通日志。

## 工具描述与 Schema 设计

工具名称应表达一个清晰动作，描述应说明适用场景、不适用场景和副作用。参数尽量使用明确类型、枚举、必填项和格式限制，避免一个 `options: object` 承载所有语义。返回值也应结构化，区分成功数据、可重试错误、业务拒绝和未知状态。

Schema 正确只代表语法正确，不代表业务语义正确。例如日期格式合法但早于允许范围，账户 ID 存在但用户无权访问。执行前必须进行业务校验和资源级授权。

## 工具粒度

工具过粗会把多个副作用绑在一起，难以审批和补偿；工具过细会增加调用轮次，让模型负责过多低层编排。合适粒度通常对应一个有明确权限、输入、输出和失败边界的业务能力。

查询与提交最好分开，例如 `prepare_transfer` 返回预览和确认令牌，`confirm_transfer` 才执行。这样用户能确认金额、对象和费用，也便于把风险操作放入确定性状态机。

## 只读操作与副作用

只读工具不等于零风险：搜索可能泄露查询，数据库读取可能越权，网页抓取可能触发 SSRF。具有副作用的工具还需区分可逆、可补偿和不可逆操作，并设置不同的确认、权限和审计策略。

删除、支付、发送消息、发布内容、权限变更等高风险动作，应在执行前展示具体目标和参数并获得确认。模型不能把历史对话中的“可以”泛化为之后所有操作的授权。

## 超时、重试与未知结果

超时只说明调用方没有在期限内得到确定结果，服务端可能已经执行。查询操作通常可以退避重试；副作用操作必须使用幂等键、请求状态查询或业务补偿，不能因为客户端超时就直接再次提交。

错误至少分为瞬时基础设施错误、限流、参数错误、业务拒绝、权限拒绝和未知结果。只有明确可重试的类别才进入带抖动的指数退避；重试还要受总时限和次数预算限制。

### 发消息接口超时后能不能重试

不能因客户端超时就直接重发，因为消息可能已发送而响应丢失。使用表示同一发送意图的幂等键，先查询下游状态或返回已保存结果；只有确认未执行且仍在截止时间内才重试。

## 幂等设计

幂等键应表示同一个业务意图，而不是每次重试都生成新值。服务端需要在持久化存储中原子地记录键、请求摘要和结果；同键同参数返回已有结果，同键不同参数应拒绝。只在客户端内存去重无法覆盖进程崩溃和并发请求。

幂等并不等于回滚。已发送的邮件可能无法撤回，外部系统也可能不支持幂等；此时需要先查询状态、使用唯一业务键，或进入人工处理和补偿流程。

## 并行工具调用

无依赖、只读且资源允许的工具可并行，例如同时查询多个资料源。存在写写冲突、先后依赖、共享预算或速率限制时应串行。并行结果合并必须保留来源和局部失败，不能因一个工具失败就默默丢弃全部结果。

模型提出多个调用时，控制器仍需构建依赖图。工具顺序不能仅由返回数组位置决定，关键约束应由代码表达。

## 取消与补偿

取消模型等待不等于取消工具，取消工具也不等于撤销副作用。取消信号应传递到网络请求、子进程和队列任务；工具返回后仍要检查任务代次，防止旧结果写入新状态。

对于已发生的动作，状态应记录 `completed`、`unknown` 或 `compensation_required`，由业务流程决定补偿或人工处理。不能向用户宣称“已取消”而忽略已提交的外部请求。

### Agent 被取消后已经发出的请求怎么办

先向下游传播取消信号，再查询外部系统确认请求状态。未执行可安全结束；已执行要保留结果；结果未知则进入查询、补偿或人工处理。取消只停止后续工作，不自动撤销已发生的支付、消息或写入。

## 权限、沙箱与凭据

工具采用最小权限：每个 Agent、用户和任务只获得所需资源与动作。文件工具限制工作区和路径穿越；网络工具限制协议、域名、重定向和私有地址；代码执行限制容器、资源和超时；数据库工具优先参数化查询和只读账户。

凭据由运行时注入工具，不应放进 Prompt。工具返回内容也属于不可信数据，必须与系统指令隔离，并限制长度、类型和可被模型解释的范围。

## Prompt Injection 与间接注入

网页、邮件、文档或工具结果可能包含“忽略之前指令”等恶意文本。该文本是数据，不具有授权能力。系统应标注来源，避免把内容拼进高优先级指令，过滤危险动作，并在执行前重新检查权限和用户意图。

单纯在 Prompt 中说“不要被攻击”不构成安全边界。真正的边界是工具白名单、参数约束、数据隔离、最小权限、风险审批和审计。

## 常见失败场景

- 工具参数通过 JSON Schema，但资源不属于当前用户。
- 写操作超时后直接重试，产生重复订单或消息。
- 工具返回网页恶意指令，模型据此调用高权限工具。
- 把工具异常转成空结果，模型误以为“没有数据”。
- 取消任务后旧工具结果继续写入当前会话。
- 工具描述重叠，模型长期在两个近义工具间选错。

## 生产实现检查表

工具注册表记录 Schema、风险、权限和超时；控制器做语法和业务校验；副作用操作绑定幂等键和审批；错误分类后再重试；工具执行支持取消；返回结果限制大小并标注来源；敏感数据脱敏；Trace 可关联模型回合和外部调用；用模拟工具覆盖成功、超时、未知结果和恶意返回。

## 20 秒口述

Tool Calling 只是模型提出结构化动作，真正执行必须经过控制器。我会对工具做 Schema 和业务校验、资源级授权、超时与错误分类；查询可以受控重试，副作用操作依赖持久化幂等键、状态查询和人工确认。工具结果同样是不可信输入，不能因为来自工具就拥有更高指令权限。

## 1 至 2 分钟展开

我先把工具定义成单一职责的业务能力，描述清楚适用条件、副作用和返回状态。模型返回调用后，控制器验证参数、权限、预算和用户授权，再执行适配器。对于写操作，每个业务意图使用稳定幂等键；超时进入未知状态，先查结果而不是直接重试。取消信号贯穿网络和子任务，但已发生的副作用要单独补偿。最后用 Trace 和模拟工具测试参数错误、限流、超时、重复提交与 Prompt Injection。

## 高频追问

### Function Calling 能保证参数正确吗

结构化输出能提高格式合规性，但不能保证字段含义、资源权限和业务约束正确。应用仍需执行 Schema、跨字段、数据库状态和授权校验。

### 怎样选择人工确认点

根据影响而不是工具名称判断。不可逆、外部通信、资金、权限、敏感数据和超出原授权范围的动作需要确认；确认内容应展示具体动作和影响。低风险只读动作可自动执行，但仍受权限和隐私边界约束。

### 怎样测试工具调用

使用确定性的 Fake 或 Mock 工具覆盖工具选择、参数、调用顺序、局部失败、超时、重试、取消和幂等；再在隔离环境做少量真实集成测试。评测必须检查外部状态，不能只看模型生成的调用 JSON。

## 系统设计练习

设计客服退款 Agent 时，查询订单和政策是只读工具；退款资格由规则服务计算；模型负责解释和收集缺失信息；`prepare_refund` 生成预览；用户确认后 `execute_refund` 使用订单与退款意图生成的幂等键；超时先查询退款状态；超过金额或规则例外转人工。
