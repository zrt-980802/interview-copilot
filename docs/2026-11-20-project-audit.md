# 项目批量测试与优化计划

日期：2026-11-20。分支：`codex/speech-pipeline`，工作区含此前未提交改动。

本轮结论：既有功能回归通过，但“是否值得回答、是否收齐条件、是否忠于个人事实、技术结论是否正确”仍存在可复现的问题。优先修复语音到问题的决策和回答上下文，再改善模型选择、资料检索及手机端状态。

本轮增加测试脚本、合成题库和报告，没有修改产品业务逻辑、默认语音流程或模型设置，没有启动实际录音。服务仍在 8527/8528，当前为兼容语音流程，麦克风测试模式和两路采集均关闭。

## P1：优先修复

### 1. 非问题被直接提交

复现：`wait_request`、`wait_short`、`audio_check`、`camera_request`、`scenario_intro`，干净/低音量两种输入共 10 次均误成题。例如“请稍等一下，我看一下你的简历”“请打开摄像头”“我先介绍一个场景”。这些输入的转写本身正确。

根因：`services/question_flow.py:24` 把“请”“介绍”和问号视为问题信号；`is_non_question` 主要覆盖语气词和典型幻觉。兼容流程也会把多数操作指令和场景铺垫直接提交。

优化：区分操作指令、音频确认、背景、场景铺垫、技术问题和同题补充。高确定性的操作指令本地处理；复杂语句结合前文和当前问题判断。不要单纯扩大一个关键词白名单。

### 2. 有效命令式问题不提交

复现：“说说三次握手”“列举常见的数据库死锁原因及排查顺序”“对比一下进程与线程的开销和隔离性”。6 次音频变体均停在待确认；“你再展开一下”的追问也被拦住。

“说说三次握手”的转写无错误，端点概率约 0.98，却不成题。根因在 `services/speech_turns.py:128` 对新问题要求显式问句信号，词表没有覆盖这些实际提问表达。

优化：与上一项共用意图判断，分别测误触发和漏触发；结合对话恢复“展开一下”的对象。不要通过取消全部过滤来修复漏题。

### 3. 已成题后的补充条件被留在草稿

复现 `complete_then_constraint`：先说“如何保证库存不能超卖”，停 3 秒，再说“补充一下，库存和订单使用两个不同的数据库”。干净/低音量两次都只提交前一句；后一句识别正确、端点概率约 0.99/0.93，却停在 `needs_review`。

`server.py:624` 的同题修订逻辑只有收到正式 `speech_commit` 才执行，新草稿的问句门槛挡住了这个没有问号的补充，模型因此可能持续沿用错误的单库假设。

对照样例“重复消费”停 5 秒后补充 ACK 失败，则正确合并为一次完整提交。测试允许“一次完整提交”或“两次提交后同题修订”，没有强制某种分段方式。

优化：让新草稿能带着前一题身份提交“补充提案”，保留新题/补充区分；修订同一个 turn，取消旧回答并更新桌面、手机和历史。本人开始回答、明确换题后应结束补充归属。

### 4. 低音量错误文字仍直接成题

复现 `short_question:very_quiet`：原文“幂等键的设计和失败重试的处理”，转为“明等片的设计和区外红区的处理”，仍自动提交。另有低音量背景流程被转写成技术感很强的文字后误成题。

72 个宽泛回放中，6 个预设覆盖失败集中在极低音量加噪声；其中 4 个虽提交数量正确，文字错误已超过本轮 15% 的筛查阈值。该阈值只是测试报警线，不是产品可直接使用的置信度。

优化：结合输入电平/信噪比、识别质量、术语和句法异常做分级处理。明显损坏先待确认；保存原文和修复候选。可推测技术近音词，数字、否定、角色和关键约束必须保留或澄清。

### 5. 经历题被判成通用技术题，简历被清空

确定性复现：“你主导的订单系统做了哪些性能优化”“你做的这个项目有哪些难点”“你带领团队解决过什么问题”。`answer_scope` 判为 `technical`，`scope_reference` 将 `resume` 设为空。

对应代码为 `services/answer_context.py:20` 和 `:60`。模型用例 E01 重复测试中一次进一步声称“现有材料里没有订单系统”，但合成简历原本就包含订单接口经历。

优化：保留经历对象和前文指代，个人事实范围不确定时保留精简履历，不因为一个分类结果完全移除。补齐“主导/做的/带领”等表达及同义改写的对照，并继续验证通用技术题不会被无关履历污染。

### 6. 模型补造未知的个人事实

主模型 X14 把“未提供分库分表实施记录”写成“没有实际落地”，还补出“单库 PostgreSQL”；X17 代填“能接受合理加班”；X15 对毕业月份冲突建议说“预计毕业”，额外推断了尚未毕业。

备用 GLM 的 X17 还给出了“一到两周内到岗”。因此换模型不足以解决。

优化：将明确支持、本人确认、未知、冲突、已排除的字段传到回答约束。正向和否定经历都要有依据，薪资/到岗/加班等个人偏好单独处理。缺项应简洁留空或待确认，不输出可直接误读为本人承诺的话术。

### 7. 技术答案格式正确，结论仍会错误

开发侧逐条审查发现的代表性错误：

| 用例 | 实际问题 | 应核对的边界 |
| --- | --- | --- |
| X01，第 0 次 | Outbox 发出后再标记，却声称“不重发” | 发送成功、标记前崩溃会重发，仍需消费者幂等 |
| X04 | 把写前检查锁归属列为保护过期写的替代方案 | 检查与下游写之间仍有竞态，应由下游校验有效 fencing token 等约束 |
| X06 | 将新版错 2、旧版错 3 读反，并声称观察差异方向可能反转 | 样本上的错误数方向已知；统计显著性另需判断，不能混为一谈 |
| X25 | 丢失更新例子归属写反，追问又与锁边界解释矛盾 | 按实际时序核对哪次更新被覆盖，临界区不可拆散读改写 |
| X30 | 声称客户端用最终 ACK 拒绝旧连接 | 应核对 TCP 的状态和 RST/ACK 作用，不能用口号替代消息协议 |

这些输出都没有触发既有格式检查。优化应包含数字/对象映射、必要条件/充分条件、事务与外部副作用边界、协议时序的固定复核样例。不能仅增加“更专业”的提示词，也不能把“引用行号有效”视为结论正确。

## P2：体验、检索和评测

### 8. 端点低分后只等待，原因展示不准确

`duration_numbers` 的数字和题意转写正确，却因端点约 0.43/0.07 未提交。`services/speech_turns.py:92` 在同次讲话活动下只请求一次端点，后续安静不会再请求。超过 8 秒后统一展示“尚未确认说完”，连高端点但缺问句信号的情况也显示这个原因。

建议：对中文短题和命令式表达校准端点，增加有界复评和明确的状态原因。保留转写失败、意图不明、端点低分、后续补充等区分，避免笼统降低阈值造成抢答。

### 9. 损坏专名可使标题过滤清空正确候选

真实混合检索对照中，Function Call 协议题的词法基线有 3 个片段，向量检索有 6 个候选，最终增强结果却为空。

另用两篇合成文档确定性复现：错误专名 `Gephi-SK` 命中文档标题，而真正解释 Function Call/schema 的文档标题为“工具调用规范”；最终返回空结果。`services/corpus.py:245` 的标题命中集合与 `:287` 的硬过滤会在正文聚焦之后删除真正相关的候选。

建议：未经确认的损坏专名不应成为强制来源范围。标题先作为排序信号，只有明确点名、来源身份可靠时才限定；对协议/机制等核心问点保留独立召回。建立“改写、错词、对象一致、来源充分”的人工标注检索集，不能只看是否有命中。

### 10. 手机看不到待确认状态

浏览器复现：电脑有补充草稿并显示“待确认”，手机仍显示旧问题和“已完成”，没有待处理提示。手机投影不含草稿是现有边界，但现在也没有任何处理进度提示。

建议：为手机提供不含草稿正文的状态，如“问题待确认”“正在合并补充”；保持手机不采集、不控制桌面。电脑端把待确认原因与当前题目关联，保留一键确认/修订，不用用户在多处寻找问题。

截图：本地 `data/project-audit-20261120/screenshots/desktop-pending-390.png` 与 `phone-pending-390.png`。本轮未发现新的布局溢出或按钮遮挡。

### 11. 格式评测不能充当回答质量准入

主模型 100 次执行均无既有自动发现项，但上述语义错误仍存在；X28 第 2 次还输出了应用明确禁止的“方向”行，既有检查器未核对动态回答计划。

建议：把传输完成、格式、引用定位、个人事实、技术约束和长度分别计分；数字和明确协议用可验证判据，开放答案保留人工复核。固定失败输入，保留重复运行和提示词哈希，修复前后同题对照。

### 12. 备用模型可用，但不宜直接替代默认模型

本轮 95 次主模型请求的首内容 P50/P95 为约 0.67/0.94 秒；7 次 GLM 对照为约 3.72/9.55 秒，完整回答中位约 11 秒。样本、难度和并发不同，这不是模型总体排名，也不含采集/检索/浏览器时间。

GLM 部分题目改善，同时仍有事实越界和不严谨表述。建议保持主备设置，先修输入归属与事实约束，再用相同失败题评估候选模型；高风险深挖可单独选择质量模型，不为所有短问增加延迟。
