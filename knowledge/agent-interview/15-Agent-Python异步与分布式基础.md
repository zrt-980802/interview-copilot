# Agent Python 异步与分布式基础

同义词：asyncio、async/await、Event Loop、事件循环、Coroutine、协程、Thread、线程、Process、进程、GIL、Queue、消息队列、Idempotency、幂等、Outbox、事务发件箱、Distributed Lock、分布式锁。本文是 Agent 后端岗位的通用基础资料。

## 一句话结论

Agent 后端大量时间花在模型、数据库和工具 I/O，Python 异步可用少量线程管理许多等待任务；但 CPU 重工作、阻塞库、副作用、跨进程一致性和重启恢复仍需要线程/进程隔离、持久化队列、幂等与状态机。

## 事件循环与协程

`async def` 调用返回协程对象，在被 `await` 或创建为 Task 后由事件循环调度。当协程 `await` 一个非阻塞 I/O 时，它让出控制权，循环运行其他就绪任务。

协作式调度意味着一段不 `await` 的长 CPU 计算或同步网络调用会阻塞整个事件循环。库必须真正支持异步；仅在同步函数前写 `await` 不会让它变成非阻塞。

### async 一定比同步快吗

不一定。它主要提高高并发 I/O 等待时的资源利用率，不会让单个外部 API 更快，也不会加速 CPU 算法。对小量简单请求，同步代码可能更易维护。是否选异步要看并发数、I/O 占比、库支持和调试成本。

## Task 生命周期与结构化并发

创建后不管的后台 Task 可能在请求结束后丢失异常，或在服务关闭时留下半完状态。使用 TaskGroup 等结构化并发，让父任务拥有子任务的启动、失败、取消和收尾。

并发子任务需要定义失败语义：一个失败是否取消所有其他任务，还是收集部分结果。不要使用宽泛异常捕获把失败转成空值，否则 Agent 可能把“工具故障”解释为“没有数据”。

## 取消、超时与清理

取消是协作式信号，只在代码到达可取消点时生效。捕获取消异常后应完成必要清理并继续传播，不能当普通错误吞掉。对于不支持取消的同步库或外部副作用，本地 Task 停止不等于工作已撤销。

超时使用绝对截止时间或剩余预算向下传递，防止每一层都重新给完整超时。清理逻辑使用 `try/finally` 或异步上下文管理器，关闭连接、归还信号量和标记任务状态。

## 信号量、连接池与背压

创建千上万个协程很便宜，但下游连接、模型限额和内存并不无限。用 Semaphore 或有界 Worker Pool 限制每个下游的并发，连接池大小与数据库容量对齐，队列有上限且输入方能感知背压。

如果请求排队时间已超过剩余截止时间，应尽早拒绝而不是白白消耗资源。每租户限额防止一个用户占满全局并发。

## 线程、进程与 GIL

对不支持异步但主要等待 I/O 的库，可用有界线程池避免阻塞事件循环。对纯 Python CPU 密集工作，常见 CPython GIL 构建下多线程通常不能线性加速，可使用进程池、原生扩展或独立计算服务。

进程之间不共享普通 Python 内存，传输需要序列化且有额外成本。不要将包含打开连接、锁或大模型对象的状态直接提交给进程池。

### 怎样把同步工具接到 async Agent

对主要等待 I/O 的同步工具，放到有界线程池，并用信号量控制对下游的并发；对 CPU 密集工具使用进程池或独立服务。需要明确线程中的阻塞调用不一定支持强制取消，超时后要拒绝过期结果并处理外部副作用。

## 线程安全与竞态条件

在单事件循环中，任务也可在 `await` 之间交错，读-改-写序列跨越 `await` 仍可产生竞态。使用锁、原子数据库更新、乐观版本或单写者模式，并尽量不在持锁时调用远程 API。

进程内锁不能保护多进程或多实例共享资源。业务一致性优先依靠数据库唯一约束、事务和状态版本，而不是用分布式锁包住所有操作。

## 队列交付与幂等

分布式队列通常不能同时保证任意故障下绝对不丢失且绝对不重复。工程上常采用至少一次交付加幂等消费者：业务意图有稳定键，数据库原子记录键、参数摘要和结果，重复交付返回旧结果。

消息确认只在业务状态安全持久化之后发生。失败分为可重试、业务拒绝、永久无效和未知结果；死信队列需要告警、可观测和人工处理，不是沉默终点。

## 事务发件箱 Outbox

服务同时更新数据库和发送消息时，两个独立操作之间可崩溃，导致数据已改但事件丢失，或事件已发但数据回滚。Outbox 将业务更新和待发事件写入同一数据库事务，再由独立 Relay 发布。

Relay 仍可重复发布，消费者还需幂等。Outbox 解决本地事务与消息的原子可见性，不是分布式全局事务。

## 一致性、补偿与 Saga

跨多个外部系统的 Agent 操作通常无法共享 ACID 事务。将流程表达为持久化状态机，每个步骤有幂等执行、明确成功证据和可能的补偿。补偿是新的业务动作，不一定恢复到从未发生的状态。

对不可逆动作，通过预留、确认或先做风险检查将它推迟到流程后段。任何补偿失败都进入可观测的人工处理状态。

## 常见失败场景

- 在 `async` 函数中直接调用同步 HTTP 或 CPU 重任务，阻塞整个循环。
- 创建后发 Task 不保存引用、不收集异常，关闭时丢失。
- 吞掉取消异常，用户已停止但工具仍继续调用。
- 无界创建协程，连接池、限额和内存被耗尽。
- 把进程内锁当成多实例全局锁，并发写入覆盖。
- 假设队列绝对一次交付，Worker 重启导致重复副作用。

## 生产实现检查表

事件循环不运行阻塞 I/O 或 CPU 重任务；结构化管理子 Task；取消和截止时间向下传递；清理使用 finally 或上下文管理器；下游并发用信号量与有界队列；状态更新用事务、唯一约束或乐观版本；队列消费者幂等；消息与数据库用 Outbox 协调；跨系统操作有持久化状态和补偿；死信可告警与人工处理。

## 20 秒口述

Python async 适合 Agent 大量模型和工具 I/O，协程在 await 时让出事件循环。同步阻塞库用有界线程池，CPU 重工作用进程或独立服务。长任务进持久化队列，用至少一次交付加幂等、Outbox 和状态机处理故障。

## 1 至 2 分钟展开

事件循环适合管理许多等待中的模型、检索和工具请求，但代码必须在 I/O 点真正让出。我会用 TaskGroup 管理子任务，明确部分失败语义，将取消和剩余截止时间向下传。下游并发用信号量限制，阻塞库进线程池，CPU 任务进进程池或独立 Worker。如果任务需要跨请求持续，放入持久化队列，假设会重复交付，用业务幂等键和数据库约束保证结果。数据库事务与消息用 Outbox 衔接，多系统副作用用持久化 Saga 和补偿处理。

## 高频追问

### 协程和线程怎么选

对已有异步客户端、高并发 I/O 和需要结构化取消的代码用协程。对无法改造的同步 I/O 库用有界线程池隔离。两者都需并发上限；线程还需要关注共享内存同步。

### 分布式锁能解决重复执行吗

不能单独解决。锁可过期、持有者可暂停，网络分区后还需要 fencing token 拒绝旧持有者。对副作用，核心仍是稳定业务幂等键、数据库唯一约束和状态机，锁只是减少并发冲突的优化。

## 系统设计练习

设计异步 Agent 任务服务：API 以用户和意图生成幂等任务，在数据库同一事务写任务与 Outbox；Relay 发布到队列；Worker 取得租约，按状态版本执行；工具写操作有独立幂等键；结果提交使用乐观更新；重复消息返回已有结果；失败按类型重试或进死信；取消更新任务世代并传递信号。
