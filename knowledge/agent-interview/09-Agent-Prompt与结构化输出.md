# Agent Prompt 与结构化输出

同义词：Prompt Engineering、System Prompt、Developer Instruction、Few-shot、Structured Output、JSON Schema、Constrained Decoding、Prompt Versioning、提示词工程。本文是通用技术资料，不证明候选人进行过相关实验。

## 一句话结论

Prompt 是可版本化的行为配置，不是安全边界或业务逻辑。好 Prompt 说清目标、输入边界、可用动作、输出契约和不确定时的行为；结构化输出只能提高格式可解析性，不能保证事实、权限或业务语义正确。

## Prompt 的分层职责

稳定的产品政策放在高优先级指令，当前任务和用户要求作为输入，检索文档、网页和工具结果明确标记为不可信数据。不要将外部内容与系统规则拼成一段无边界文本。

Prompt 应尽量告诉模型“成功产物是什么”和“缺什么时怎么做”，而不是堆叠大量抽象形容词。可以要求结论、证据、未确定项和下一动作，但不依赖模型暴露私有思维链。

## 明确的输入边界

为用户输入、参考资料、工具返回和历史状态使用结构化容器或消息边界，并提供来源、时间和信任等级。分隔符提高可读性，但不是安全隔离；外部文本仍可包含恶意指令。

上下文中只保留对当前决策有用的内容。指令、证据和历史摘要要分开预算，防止参考文档挤掉工具 Schema 或用户核心约束。

## Few-shot 与示例

示例适合展示输出边界、分类标准、特殊错误和语气。示例应覆盖正常、边界和应该拒绝或澄清的情况，不只是几个理想答案。

示例也会引入偏差。不要让所有示例拥有同一长度、领域或答案顺序；不要在示例中放真实密钥和个人数据；示例变更需进入回归评测。

## 结构化输出与约束解码

JSON mode 通常只保证输出是 JSON，不保证符合具体 Schema。基于 Schema 的约束输出可限制字段、类型、枚举和必填项，但不同模型或提供商支持的 Schema 子集可能不同。

应用必须再次验证：语法 Schema、跨字段约束、数据库状态、资源归属和当前用户权限。输出失败时区分可修复的格式错误、需要澄清的业务缺失和不应重试的授权拒绝。

### 结构化输出能防幻觉吗

不能。它可以保证 `date` 是字符串，但不保证日期是真的；可以保证 `tool_name` 属于枚举，但不保证工具适合当前任务。事实需要证据，动作需要权限与业务校验。

## Prompt 版本化与评测

每次请求记录 Prompt 模板版本或哈希、模型、参数、工具 Schema 和检索版本，但日志对敏感输入脱敏。修改前在固定评测集上对比任务成功、格式合规、工具选择、拒绝过多、延迟和 Token。

不要只优化一个展示样例。Prompt 会与模型版本、Context 长度、工具数量和数据分布交互，需要分层错误分析和线上监测。

## Prompt 不应承担的职责

权限检查、金额上限、资源范围、请求频率、交易幂等和完成判定应在确定性代码中。“绝对不要泄露密钥”是有用的行为指导，但正确设计是让模型根本看不到密钥。

当规则较多且可编程时，用策略引擎或代码筛选，只把需要语义判断的窄问题交给模型。

## 常见失败场景

- Prompt 指令相互矛盾，没有说清优先级或失败行为。
- 用更多形容词修补栶心工具和证据不足。
- 过度针对少数示例，新领域或否定句性能下降。
- JSON 通过解析就直接执行，未做语义、资源和权限验证。
- 外部文档被拼入系统指令区，间接 Prompt Injection 获得高优先级。
- 线上修改 Prompt 没有版本、回归集和回滚。

## 生产实现检查表

明确目标、非目标和失败行为；区分指令与不可信数据；限制 Context 预算；用代表性 Few-shot 而非只有理想例；输出有 Schema 且应用层二次验证；安全和业务规则由代码强制；Prompt、模型和工具版本可追溯；变更运行回归和安全集；监测格式失败、过度拒绝、延迟和成本。

## 20 秒口述

Prompt 是可版本化的行为配置，我会写清目标、输入边界、可用动作、输出 Schema 和不确定时的处理。结构化输出只保证格式，应用还要做业务和权限验证。权限、幂等和安全不交给 Prompt。

## 1 至 2 分钟展开

我会先把稳定政策、当前任务和外部资料分层，明确文档和工具结果是不可信数据。Prompt 不只要描述理想结果，还要说明缺信息、来源冲突和无权时怎么做。如果需要结构化输出，使用 Schema 约束并在应用层重新验证。所有变更记录 Prompt 版本、模型和工具 Schema，在固定题集上比较成功率、格式合规、过度拒绝和成本，而不凭一个 Demo 判断。

## 高频追问

### Prompt 越长越好吗

不是。过长 Prompt 可能产生矛盾、稀释关键约束并增加延迟。优先保留目标、安全边界、动作和输出契约，把可编程规则移到代码，用消融评测判断每部分是否真有价值。

### 输出 Schema 应该设计多细

细到应用能稳定判断和执行，但不把模型变成补齐大量无用字段的模板引擎。必填字段应真正必需，枚举要有未知或需澄清的表达，并对 Schema 演进做兼容策略。

## 系统设计练习

设计工单分流 Prompt：输入明确分为用户原文、客户元数据和不可信附件；输出 Schema 包括类别、置信度、需要的缺失字段和证据摘要；低置信度转人工；客户权限和队列路由由代码判定。回归集覆盖否定、多意图、附件注入和无法分类。
