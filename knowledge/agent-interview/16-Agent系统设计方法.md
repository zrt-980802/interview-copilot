# Agent 系统设计方法

同义词：Agent System Design、智能体系统设计、Requirements、需求澄清、SLO、State Machine、状态机、Trust Boundary、信任边界、Capacity Planning、容量规划。本文是通用答题方法，不代表候选人实现过某个系统。

## 一句话结论

Agent 系统设计要从用户任务、成功标准和失败代价开始，再定义权限、状态、控制流、工具、数据、故障恢复和评测。模型与框架是满足约束的部件，不是答案的起点。

## 八步答题骨架

1. 澄清用户、任务、上下游、非目标和规模。
2. 定义成功条件、禁止动作、延迟与费用 SLO。
3. 划分信任边界、身份、资源权限和人工确认。
4. 定义权威状态、生命周期、检查点和幂等键。
5. 画主链路：输入、规划/路由、检索、工具、验证与输出。
6. 设计超时、重试、取消、补偿、降级和人工接管。
7. 补充可观测、安全、隐私、部署和容量。
8. 说明离线评测、上线节奏、指标和一个关键取舍。

面试中不需要机械念完八步。先说最影响架构的两个澄清问题，给出主链路，再根据面试官追问深入状态、安全或性能。

## 需求澄清

### 设计 Agent 系统时第一步应该问什么

先问目标用户和高频任务，尤其是系统只给建议还是会执行副作用，因为这决定授权、审批、幂等和验证方式。随后澄清可验证成功、禁止动作、延迟/成本 SLO、数据与规模，再进入架构。

首先问目标用户、高频任务、是只给建议还是可以执行副作用。明确数据源、工具数量、日请求量、峰值并发、单任务平均时长、个人数据和合规约束。

高度影响设计的问题要先问：需要实时返回还是允许异步？失败能否降级为建议或必须阻断？输出是帮助人判断，还是直接改变资金、权限或外部通信？

## 成功、风险与 SLO

把成功表达为可验证的外部状态或产物，例如“目标测试通过且修改未越界”，不是“模型说已修复”。同时列出禁止动作，例如越权读取、未确认写入和伪造引用。

将响应分成首个有用反馈、完整任务完成和截止时间。指标不只有延迟，还包括任务成功、风险事件、人工接管、用户纠正和每成功任务成本。

## 信任边界与授权

画出用户、Agent 运行时、模型提供商、检索系统、工具、业务数据库和第三方服务。指令和外部数据分离，模型不直接拥有凭据，每次工具在服务端重新做资源级授权。

根据影响将工具分为只读、可逆写入、可补偿和不可逆。高风险动作使用 prepare-confirm-execute 两阶段，确认绑定具体参数，执行时重新授权。

## 状态模型

状态至少包含任务 ID、用户目标、已确认事实与来源、待办步骤、工具调用记录、预算、审批、当前世代和终止状态。权威状态存在应用存储，模型 Context 只是当前调用的投影。

短请求可以临时执行，但只要有多步副作用、长任务、人工审批或重启恢复，就需要持久化状态机和检查点。幂等键表示业务意图，世代号防止旧 Worker 回写。

## 主执行链路

输入层先做身份、大小、类型和恶意文件检查。Router 或 Planner 判断是固定 Workflow、单 Agent 还是需要子任务。Context Builder 从状态、Memory 和检索组装受预算限制的输入。

模型输出结构化动作，Controller 做 Schema、业务、权限和预算检查，再执行工具并写入 Observation。Verifier 根据权威状态决定完成、继续、重规划、澄清或人工接管。

## 故障模型

分别讨论模型超时/限流、检索无结果、工具参数错误、写操作结果未知、队列重复交付、Worker 崩溃、用户取消、人工长时间不审批和下游持续故障。

对每类失败说明检测信号、可否重试、是否幂等、状态如何保存、用户看到什么和如何恢复。这比笼统说“加重试和容错”更能体现系统设计能力。

### 工具超时后怎样设计

先根据只读还是副作用区分。只读可在截止时间和次数内退避重试；写操作超时是未知结果，先用幂等键查询状态，已执行保留结果，未执行才重试，无法确认则进人工或补偿。

## 数据与存储

区分任务事务状态、对话与事件日志、文档原文、搜索索引、Embedding、长期 Memory、大型产物和观测数据。不要用一个向量数据库代替所有存储。事务状态需要约束与更新语义，大文件需要对象存储，检索索引可以重建。

数据模型保留租户、用户、来源、时间、版本和保留期。删除用户数据时追踪原文、派生摘要、Embedding、缓存、Trace 和评测副本。

## 容量估算

使用峰值到达率与平均服务时间初步估算同时在途任务，再加重试、长尾和峰值余量。估算每任务平均模型轮次、输入/输出 Token、工具调用、存储和 Trace 体积。

指出真正瓶颈可能是模型配额、下游 API、数据库连接或人工审批，并通过信号量、租户配额、有界队列和降级保护。精确数字不是必须，但要有可计算的假设和瓶颈意识。

## 观测与评测

根 Trace 连接模型、检索、工具、状态与人工节点。指标分为结果、轨迹和系统三层。安全和数据越权作为独立门禁，不被平均质量分数抵消。

评测集包含正常、歧义、无答案、下游故障、副作用未知、取消、攻击和租户隔离。从离线 Fake 环境、真实集成、Shadow 到 Canary 逐步增加现实性和风险。

## 常见失败场景

- 一开始就选模型和框架，没有定义用户、成功与风险。
- 只画完美主链路，不讨论超时、重启、取消和未知结果。
- 把对话历史当成权威任务状态，重启后副作用无法对齐。
- 只用模型自评判定完成，没有外部验证。
- 容量估算只算 API QPS，忽略多轮、工具、重试和长任务。
- 一个平均分数掩盖数据泄露或重复扣款等严重失败。

## 生产实现检查表

用户、任务和非目标清晰；成功与禁止动作可验证；有延迟、质量和费用 SLO；信任边界和资源授权明确；权威状态持久化；执行链路区分模型建议与控制器决定；常见故障有恢复语义；存储按语义选择；容量有可计算假设；观测与评测覆盖结果、轨迹和系统。

## 20 秒口述

设计 Agent 我会先问目标用户、任务、是否可执行副作用，并定义可验证成功和禁止动作。然后画信任边界和权威状态，用 Controller 校验模型动作，再补超时、幂等、恢复、可观测和评测。模型选择放在这些约束之后。

## 1 至 2 分钟展开

我会先澄清用户、高频任务、资料与工具、规模，尤其是 Agent 只给建议还是会产生副作用。然后定义权威环境中的成功条件、安全不变量和 SLO。架构上，持久化任务状态和预算，Context Builder 只组装当前必要信息；模型返回结构化动作，Controller 做权限、参数、幂等和预算检查，Verifier 用外部状态判定完成。接着我会选一个写操作超时和一个 Worker 崩溃讲恢复。最后补 Trace、容量、成本、离线评测和 Canary，并说明一个为了安全或可恢复性接受额外延迟的取舍。

## 高频追问

### 系统设计需要一开始就用多 Agent 吗

不需要。先用确定性 Workflow 加单 Agent 表达主链路。只有当子任务的工具、权限或 Context 确实需要隔离，或者独立并行有明显收益时再拆。说明拆分条件比默认画多 Agent 更重要。

### 面试时容量数字不清楚怎么办

主动给出明确假设，例如峰值每秒任务数、平均模型轮次和任务时长，用它们推导在途任务、队列和模型调用量，再说如果实际数字不同，哪个瓶颈和架构决策会变。

## 系统设计练习

设计“能读公司文档并创建工单的企业 Agent”：先限定内部用户、只读问答和创单两类任务；检索前按 ACL 过滤；答案保留引用；创单使用 prepare-confirm-execute 与幂等键；任务状态持久化；超时查工单系统状态；数据与 Trace 按租户隔离；评测覆盖无答案、越权文档和重复创单。
