# Agent 规划推理与任务分解

同义词：Planning、Reasoning、Task Decomposition、任务分解、ReAct、Plan-and-Execute、Reflection、Reflexion、Critic、Verifier、Replanning。本文描述外部可观察的规划工程，不要求模型暴露私有思维链。

## 一句话结论

规划的目标不是生成一份看起来完整的步骤清单，而是把目标转成一组有依赖、有验证条件、能根据观察结果调整的行动。生产系统应保存简洁的计划、决策依据和验证结果，不依赖输出冗长思维链来获得可靠性。

## 任务分解的基本结构

一个可执行步骤至少包含目标、前置条件、输入、允许工具、预期产物和完成验证。好的分解能缩小每一步的选择空间，并让失败定位到具体阶段。坏的分解常出现“分析问题”“完成实现”这类无法验证的步骤。

分解粒度需要平衡。过粗时模型一次承担太多约束；过细时步骤数、调用成本和错误传播增加。通常以一次工具动作或一个可独立验证的中间产物作为粒度，再根据任务复杂度动态合并。

## ReAct

ReAct 将短推理和动作交替：根据当前 Observation 选择下一工具，再用结果决定后续行动。它适合网页探索、故障诊断和步骤不确定的任务，因为每次观察都可能改变路径。

风险是局部贪心、循环和上下文膨胀。工程上应把模型输出限制为动作和简短理由，由控制器记录结构化 Trace；设置重复检测、预算和停止条件；重要结论由工具或规则验证。

## Plan-and-Execute

Plan-and-Execute 先形成阶段计划，再由执行器逐项完成。它适合依赖关系较清楚、任务较长或需要展示进度的场景。计划可以减少每轮重新理解全局目标的成本，也方便并行处理无依赖步骤。

初始计划并不可靠。执行器必须把新事实反馈给规划器，在前置条件失效、工具不可用或目标变化时修订计划。若每次细小变化都全量重规划，会增加成本并引入不稳定；应定义触发条件和受影响范围。

## 分层规划

常见生产模式是分层规划：顶层只定义少量里程碑和依赖；每个里程碑内部采用短 ReAct；完成后由验证器检查产物。这样既保留全局方向，又避免一次计划假设过多未知事实。

计划应区分事实、假设和待确认项。例如“仓库使用 PostgreSQL”如果尚未读取配置，只能是待验证假设。工具观察确认后再更新为事实，防止后续步骤基于错误前提扩散。

## Reflection、Critic 与 Verifier

Reflection 让模型回顾结果并提出改进；Critic 针对候选输出寻找问题；Verifier 使用规则、工具或独立模型检查约束。它们能发现遗漏，但并不天然保证正确，同源模型可能重复相同偏差。

客观条件优先用确定性 Verifier，例如 JSON Schema、单元测试、SQL 约束和静态检查。模型 Critic 更适合可读性、覆盖度和开放式质量。只有当反馈能触发具体修改，而且收益超过额外调用成本时才增加反思轮次。

## 重规划触发条件

重规划可由以下事件触发：关键假设被否定；工具返回不可恢复错误；权限或资源变化；计划依赖出现冲突；连续步骤无进展；用户修改目标；剩余预算不足以完成原计划。一般的瞬时错误先按工具策略重试，不必立即推翻整个计划。

重规划时保留已经验证的事实和产物，只修改受影响步骤。对已产生副作用的动作不能简单从计划中删除，应记录结果并决定继续、补偿或人工处理。

## 搜索空间与预算控制

规划本质上是在候选动作中搜索。限制允许工具、候选数量、分支深度和每阶段预算，可以减少无意义探索。对于高成本任务，可先用便宜模型生成候选，再用规则或高质量模型选择；但模型路由本身也要评测。

预算不仅是 Token，还包括墙钟时间、外部 API 费用、工具调用次数和风险额度。预算耗尽前应预留总结、持久化状态和请求人工输入的资源，不能在最后一步突然失去恢复信息。

## 不确定性与澄清

当缺失信息会显著改变方案或产生高风险副作用时，应先澄清；如果只是低风险实现细节，可以声明合理假设并继续。澄清问题应具体到可选项和影响，而不是笼统询问“还需要什么信息”。

模型给出的置信分数通常没有校准，不能单独决定是否执行。更可靠的信号包括多个候选答案冲突、检索证据缺失、Schema 多次失败、验证器不通过和任务超出已知权限。

## 常见失败场景

- 一开始生成很长的静态计划，后续不根据工具结果更新。
- 把推断写成事实，使错误前提在多个步骤中扩散。
- 反复 Reflection 但没有外部验证，得到更自信的错误答案。
- 为简单任务增加规划器、执行器和 Critic，成本超过收益。
- 重规划丢失已发生的副作用，恢复时重复执行。
- 只限制最大轮数，没有定义任务进展和成功条件。

## 生产实现检查表

计划使用结构化步骤并带稳定 ID；每步声明依赖和验证器；状态区分事实、假设与观察；控制器限制工具和预算；执行后更新步骤状态；仅在明确事件下重规划；已完成且验证通过的步骤默认保留；副作用结果持久化；最终由任务验证器决定完成。

## 20 秒口述

我不会把规划理解成让模型一次写完整思维链，而是生成可执行、可验证、可修订的步骤。短而不确定的任务可以用 ReAct，长任务用粗粒度 Plan-and-Execute，每个阶段内部再做短循环。关键事实变化时局部重规划，客观结果用工具和规则验证，并通过步骤、时间和费用预算限制搜索空间。

## 1 至 2 分钟展开

我会让每个计划步骤包含前置条件、允许工具、产物和完成验证，并区分事实与假设。执行器完成一步后把真实 Observation 写回，验证通过才标记完成。如果关键假设失效、依赖冲突或连续无进展，就只重规划受影响部分。Reflection 可以帮助发现遗漏，但不能替代单元测试、Schema 或业务状态检查。这样既保留模型处理开放任务的能力，也能控制循环、成本和错误传播。

## 高频追问

### ReAct 的缺点是什么

它容易局部贪心、重复调用、累积长轨迹，并且每轮都依赖模型判断。可通过工具白名单、短 Observation、重复检测、预算、外部验证和阶段计划缓解，但任务能固定表达时应直接使用 Workflow。

### Reflection 一定能提高正确率吗

不一定。相同模型缺少新证据时可能只是改写原答案，甚至强化错误。应给 Critic 明确检查项，引入测试或检索等外部信号，限制轮数，并用对照评测确认收益。

### 什么时候应该向用户澄清

缺失信息会改变目标、权限、不可逆操作或主要成本时必须澄清；低风险且可回滚的细节可声明假设继续。澄清应一次询问最影响方案的变量，避免把所有不确定性都推回用户。

## 系统设计练习

设计研究报告 Agent 时，顶层计划可以是范围确认、资料收集、证据筛选、结构编排、草稿、引用校验。搜索阶段用 ReAct 动态换查询；每条主张保留来源；若关键结论缺乏证据则重规划搜索或降低结论强度；最终验证引用是否存在、日期是否满足要求，而不是让模型自行宣布完成。
