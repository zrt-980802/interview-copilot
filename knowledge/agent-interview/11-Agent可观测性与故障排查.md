# Agent 可观测性与故障排查

同义词：Observability、可观测性、Tracing、链路追踪、Span、Metrics、指标、Logs、日志、Replay、重放、OpenTelemetry、Root Cause Analysis、根因分析。本文是通用技术资料。

## 一句话结论

Agent 可观测不是保存整段对话，而是用统一 Trace 将用户请求、模型调用、工具执行、状态转移、检索、审批和最终结果关联起来，同时管理敏感数据和版本，从而回答“发生了什么、为什么、影响多大”。

## Trace 的层级

一次用户任务对应根 Trace，每个模型回合、检索、工具调用、子 Agent、审批和状态存储作为 Span。Span 记录父子关系、开始结束、状态、错误类型、重试次数、模型与工具版本，以及经脱敏的输入输出摘要。

并行工具不能只靠时间顺序推测因果，必须保留父子 ID、任务 ID 和尝试号。跨进程、队列或 Agent 交接时传递 Trace Context，但不把用户敏感数据放入可全局传播的 baggage。

## 状态转移与决策证据

对 Agent 来说，只看模型输出不足以排查。每次转移记录前置状态版本、候选动作、通过的校验、被拒绝的原因、外部 Observation 和新状态版本。完成判定要记录外部验证结果，不只是模型的文字理由。

为了解释决策，保留简短的动作理由、引用证据和规则命中就够了，不依赖或记录模型私有 Chain-of-Thought。

## Logs、Metrics 和 Traces 的分工

Logs 适合记录离散事件和错误上下文；Metrics 用于低成本聚合、告警和趋势；Traces 用于分析一次任务跨组件的因果与延迟。三者通过 Trace ID、任务类型、版本和错误码关联。

不要把用户 ID、Prompt 或工具参数作为 Metrics 高基数标签。指标使用可控维度，具体请求通过 Trace 搜索。日志需要结构化错误码，不依赖模型生成的自然语言错误描述聚合。

## 应该监测哪些指标

结果层包括任务成功、用户纠正、人工接管、禁止动作和无答案率。轨迹层包括工具选择、参数验证失败、循环步数、重复调用、重规划、检索命中和引用支持。系统层包括首个有用结果时间、端到端 P50/P95/P99、队列等待、限流、超时、Token、费用和下游错误。

指标按任务类型、风险、模型版本和发布版本分层。一个总平均值会掩盖高风险任务失败和长尾延迟。

## 完整重放为什么很难

模型采样、提供商后端、网络时序和外部数据都可变，即使温度较低也不能假设完全重现。可重现调试应保存模型、Prompt、工具 Schema、检索快照、配置和外部 Observation 的脱敏版本，并用 Fake 工具重放控制流。

### 线上 Agent 答错了怎样排查

先确认失败层：输入识别、检索、规划、工具、状态、合并还是生成。沿 Trace 检查当时版本和每次状态转移，再用保存的 Observation 与 Fake 工具复现。最后将故障转成能重复的评测案例，而不是只修当次 Prompt。

## 告警与 SLO

告警应面向用户影响和错误预算，例如高风险工具失败、任务成功率骤降、P95 超过 SLO、队列积压或成本异常，而不是每个单次模型错误都发高级告警。

将 SLI 定义为可观测的好事件比例或延迟分布，SLO 定义时间窗内目标。对任务型 Agent，技术 HTTP 200 不代表用户任务成功，需要业务成功信号。

## 敏感数据与观测成本

采用默认不记录完整敏感内容的策略，用类型、长度、哈希、字段白名单和可控的安全调试窗口替代。记录权限与普通业务权限分离，设置保留期和访问审计。

追踪也有成本。可对正常低风险任务采样，但错误、高延迟、高风险和发布 Canary 优先保留完整 Trace。采样策略不应让罕见严重错误消失。

## 常见失败场景

- 只保存最终 Prompt 和回答，无法看到工具、检索和状态转移。
- 每个服务生成不同 ID，队列之后 Trace 断裂。
- 用户 ID 和 Prompt 作为 Metrics 标签，导致基数与成本失控。
- 记录完整 Context 和密钥，观测系统变成数据泄露源。
- 只监控 HTTP 成功率，模型拒绝或任务未完成却被计为成功。
- 将无法完全复现的随机结果误当成日志缺失。

## 生产实现检查表

一次任务一个根 Trace；模型、检索、工具、审批和状态为子 Span；队列和 Agent 交接传递关联 ID；记录版本与结构化错误；结果、轨迹和系统指标分层；监控分位数和队列等待；敏感数据默认不记录；错误与高风险 Trace 优先保留；告警面向 SLO 和用户影响；生产失败脱敏后进入回归集。

## 20 秒口述

Agent 可观测要用一个 Trace 串起用户任务、模型、检索、工具、状态转移和审批。我会同时看结果、轨迹和系统指标，保留当时的版本与脱敏 Observation，用 Fake 工具复现控制流，而不承诺模型输出可完全重放。

## 1 至 2 分钟展开

我会把一次 Agent 任务当作根 Trace，每个模型调用、检索、工具、子 Agent 和状态存储建立子 Span。Span 保留任务和尝试 ID、延迟、结构化错误、版本与经脱敏的输入输出摘要。任务失败时，我先判断是检索、规划、工具、状态还是生成层，再沿状态版本和 Observation 定位。指标上不只看 HTTP，还看真实任务成功、人工接管、P95 和成本。最后把失败转成可复现的回归案例。

## 高频追问

### 需要记录完整 Prompt 吗

默认不应全量记录。优先保存模板版本、长度、哈希、数据类型和脱敏摘要。只在有授权、短保留期和严格访问控制的安全调试通道采集必要原文。

### 怎样区分模型问题和工具问题

通过 Trace 重放固定变量：先检查工具请求是否正确；如果请求正确但外部返回错，是工具或集成层；如果 Observation 正确但后续忽略，是策略或上下文问题。用 Fake 工具和固定 Observation 做消融对照。

## 系统设计练习

为客服 Agent 设计观测：根 Trace 关联用户会话和工单；检索记录文档版本与命中 ID；工具 Span 记录订单资源摘要、授权结果和幂等键哈希；退款审批作为事件；指标按问题类型追踪解决率、人工转接、P95 和重复退款门禁。
