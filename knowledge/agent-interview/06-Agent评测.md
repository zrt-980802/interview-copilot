# Agent 评测

同义词：Agent Evaluation、Evals、Benchmark、基准、Golden Dataset、黄金数据集、Task Success、任务成功率、Tool Accuracy、工具准确率、Trajectory Evaluation、轨迹评测、LLM-as-Judge、回归测试。

## 一句话结论

Agent 评测不能只判断最终文本是否好看，而应同时检查任务结果、执行轨迹和系统运行。最终结果可能碰巧正确但过程越权，轨迹可能合理但任务未完成；因此客观条件用代码和环境验证，开放质量用人工与校准后的模型评审，生产指标用于确认真实效果。

## 从成功标准开始

先定义目标用户、任务分布和失败代价，再选择指标。客服 Agent 的成功可能是正确解决且未违反政策；Coding Agent 是修改范围正确且测试通过；研究 Agent 是主要结论有可靠来源。一个抽象“回答质量分”无法覆盖这些差异。

指标要区分硬约束与优化目标。权限越界、数据泄露和重复支付属于零容忍或单独门禁；延迟、成本和风格可以做权衡，不能用平均分掩盖严重安全失败。

## 结果评测 Outcome Evaluation

结果层检查任务是否真实完成。优先读取权威环境：文件与测试状态、数据库记录、模拟业务系统、资源 ID 或用户目标状态。对于文本答案，检查事实、约束、完整性、引用和格式。

结果评测应允许部分成功和明确失败分类。例如研究报告可能找到正确来源但遗漏一个子问题。只有二元总分会隐藏改进方向。

## 轨迹评测 Trajectory Evaluation

轨迹包括模型动作、工具参数、Observation、重试、审批和状态转换。评测关注是否选择正确工具、参数是否合理、是否遵守顺序、是否重复、是否利用了工具结果，以及是否在应停止时停止。

不存在唯一正确轨迹时，不应要求与 Golden Trace 完全一致。可以定义允许的关键节点和禁止动作，或比较最终状态、调用集合与效率。轨迹评测尤其适合发现“结果正确但过程危险”。

## 系统与运营评测

系统层指标包括端到端延迟、首个有用结果时间、Token 与 API 成本、工具调用数、错误率、重试率、人工接管率、取消响应和资源消耗。使用平均值之外，还要看 P50、P95、P99 和长尾失败。

生产效果还需业务指标，例如解决率、用户纠正率、任务完成时间和投诉率。业务提升不能只归因于模型，需要对照实验和足够样本。

## Golden Dataset 建设

Golden Set 应来自真实任务分布、历史失败和高风险边界，并覆盖正常、困难、无答案、歧义、工具故障和攻击案例。每条案例包含输入、初始环境、允许权限、成功条件、禁止动作和必要证据。

数据集需要版本化和评审。只由同一个模型合成问题与答案容易产生偏好和泄漏；公开 Benchmark 用于外部比较，内部真实任务集用于产品决策。

## 模拟环境与 Fake Tools

Agent 的外部状态必须可控，测试才能复现。Fake 工具应模拟正常返回、限流、超时、未知结果、部分失败、恶意内容和副作用，并记录调用参数和顺序。测试后检查环境最终状态。

模拟器不是全部真实世界。少量隔离集成测试用于验证协议、权限和第三方差异；生产 Shadow 或 Canary 需要限制副作用，并遵守用户数据政策。

## 确定性评审

能够用代码判断的内容优先使用代码：JSON Schema、正则、单元测试、SQL 查询、权限规则、资源哈希、引用存在性和状态机不变量。确定性检查便宜、稳定、便于回归。

规则只能覆盖已表达的约束。规则通过不代表答案语义正确，因此开放任务仍需人工或模型评审，但二者不应取代硬性验证。

## Human Evaluation 人工评审

人工评审适合事实边界、帮助程度、表达质量和复杂取舍。评分标准需要具体锚点和样例，评审者应尽量盲化模型身份和版本。对主观维度可采用成对比较，通常比孤立绝对评分更稳定。

应测量评审者一致性，分歧案例进入仲裁和标准修订。人工样本用于校准自动评审，而不是只在上线前临时看几条结果。

## LLM-as-Judge

### LLM-as-Judge 能直接做上线门禁吗

不能作为唯一门禁。安全、权限、工具副作用和环境结果优先由代码与权威状态检查；LLM Judge 只用于开放式质量，并且需要明确 Rubric、交换顺序、人工校准和高风险抽检。

LLM Judge 适合大规模评估开放式答案、比较候选和提取错误类型，但会受位置、长度、措辞、同模型偏好和 Prompt 影响。Judge 可能无法访问真实环境，也可能被候选答案中的指令影响。

降低偏差的方法包括清晰 Rubric、隐藏模型身份、交换候选顺序、使用成对评审、要求基于提供证据、对高风险结果人工抽检，并定期计算与人工标签的一致性。Judge 不能成为安全门禁的唯一依据。

## 统计与不确定性

报告样本量、任务分布和置信区间，不只报告平均分。对同一批案例比较两个版本时保留配对关系；随机 Agent 可重复运行以估计方差。小样本百分比差异不能直接宣称稳定提升。

分层查看不同任务、工具和难度，避免总体平均掩盖某类退化。上线门禁可同时要求总体不下降、高风险案例全过和延迟成本在预算内。

### 怎样说明成功率提升不是随机波动

在同一批任务上做配对比较，固定数据、工具环境和评分规则；对有随机性的 Agent 重复运行，报告样本量、差值和置信区间，并按任务类型查看退化。若同时修改模型、Prompt、检索和工具，实验只能说明整套版本变化，不能把提升归因于其中一个因素。

## 回归评测与版本追踪

每次记录模型、Prompt、工具 Schema、代码、数据集和评审器版本。失败案例修复后加入回归集；但要保留独立保留集，避免长期针对固定题目过拟合。

模型服务更新可能在代码不变时改变行为，因此需要定期回归和线上漂移监测。无法重放的外部工具结果应保存脱敏快照或使用模拟器。

## 在线评测

线上观察任务成功、用户取消、纠正、人工接管、重复动作、错误和成本。隐式行为不一定代表满意，例如用户没有重试可能是放弃。关键体验仍需显式反馈和定性访谈。

A/B 测试应限定用户、时间和风险；高风险 Agent 先离线评测、Shadow、内部试用和小流量 Canary，再逐步扩大。实验日志不得泄露凭据或不必要的个人数据。

## 安全与对抗评测

安全集覆盖直接和间接 Prompt Injection、越权访问、敏感信息泄露、危险工具参数、路径穿越、SSRF、恶意文件和社会工程。测试不仅检查文本是否拒绝，还要检查工具是否真的未执行。

权限边界由系统强制，因此安全评测要验证控制器、工具和基础设施，而不只是模型防御 Prompt 的表现。

## 常见失败场景

- 只看最终答案，遗漏越权工具调用和重复副作用。
- 用同一模型生成测试、作答和评分，得到虚高结果。
- Benchmark 任务与真实用户任务分布不一致。
- 只报告平均准确率，不报告样本量和高风险失败。
- Golden Trace 规定唯一调用顺序，误判其他正确路径。
- 修改模型、Prompt 和检索后把提升归因于单一变量。

## 生产实现检查表

明确任务成功标准；建立真实任务分层数据集；用 Fake 工具控制环境；结果、轨迹和系统分层打分；硬约束代码验证；LLM Judge 经人工校准；保存完整版本；失败进入回归集；报告置信区间和错误类型；高风险案例作为独立门禁；上线后监测效果、漂移和成本。

## 20 秒口述

Agent 评测我会分成结果、轨迹和系统三层。结果用权威环境判断任务是否完成；轨迹检查工具、参数、顺序、权限和重复动作；系统看延迟、成本与人工接管。客观条件优先代码验证，开放质量再用人工和校准后的 LLM Judge，并用版本化 Golden Set 做持续回归。

## 1 至 2 分钟展开

我会先从真实任务定义成功和禁止动作，再建设包含正常、困难、故障和攻击案例的 Golden Set。Fake 工具提供可复现环境，并记录每次调用。最终状态用规则检查，轨迹允许多种正确路径但要求关键节点和安全不变量。开放式质量采用盲化的人工或成对 LLM Judge，并定期校准一致性。报告分层指标、样本量和置信区间，同时追踪模型、Prompt、工具与数据版本，避免把多变量变化误判为单一优化。

## 高频追问

### 最重要的 Agent 指标是什么

没有跨任务唯一指标。首先是任务特定成功率和安全不变量，再结合工具准确率、人工接管、延迟和成本。指标选择取决于失败代价。

### 怎样评测有多个正确路径的 Agent

验证最终环境状态、关键中间约束和禁止动作，而不是逐步匹配唯一 Golden Trace；可额外比较调用成本、重复步骤和路径长度。

### 线上失败如何进入评测集

先脱敏并还原初始状态、期望结果和失败类型，用模拟工具复现；修复后加入回归集，同时保留独立保留集，避免只针对历史案例优化。

## 系统设计练习

评测 Coding Agent 时，结果层检查目标测试、静态检查和差异范围；轨迹层检查是否读取相关文件、是否修改越界、是否运行必要测试、是否执行危险命令；系统层记录耗时、Token 和命令数。数据集覆盖正常需求、含糊需求、测试故障、依赖缺失和恶意仓库指令。
