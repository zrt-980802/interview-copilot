# Agent 项目追问与技术表达

同义词：Project Deep Dive、项目深挖、STAR、Architecture Decision、架构决策、Trade-off、取舍、Incident Review、故障复盘、Metric、指标、Resume Interview、简历追问。本文只提供表达框架，不提供或推断候选人的项目事实。

## 一句话结论

项目深挖的好答案不是罗列技术栈，而是说清真实问题、自己的责任、关键约束、做过的决策、证据、结果与不足。没有做过的方案应说“我会这样设计”，没有测量的改进不能编造数字。

## 一分钟项目开场

用五句话建立全局：为谁解决什么问题；原先痛点和可验证目标；系统主链路；自己直接负责的部分；最重要结果和当前边界。

例如语法骨架：“这是面向 [用户] 的 [产品]，主要解决 [问题]。当时的关键约束是 [约束]。主链路是 [输入-控制-工具-验证]。我主要负责 [实际工作]。我们用 [指标/证据] 观察到 [结果]，但 [尚未解决] 仍是边界。”只填有资料支持的内容。

### 如何用一分钟介绍 Agent 项目

按“用户与问题—可验证目标—主链路—个人责任—结果与边界”五句话展开。只说有事实支持的规模和指标，先建立全局，把模型选择、工具、恢复和评测细节留给追问。

## 用主链路讲架构

架构回答按一次真实请求顺序：输入如何进来，身份和任务怎样建立，Context 如何组装，模型决定什么，代码强制什么，工具怎样调用，结果怎样验证和呈现。

主链路讲完再说两条横切面：状态/恢复以及安全/观测。不要一开始就从数据库、消息队列、向量库一路列名词，面试官需要先理解数据流和责任边界。

## 说清个人贡献

用动词和产物表达：我定义了什么契约，实现了哪个链路，建立了哪组评测，定位了什么故障，推动了什么决策。“参与”和“负责”太宽，要说边界和协作者。

团队成果可以说“我们”，但紧接着说“我的部分是”。不把他人的模块说成自己实现，也不因为不是独立完成就无法讲技术取舍和协作。

### 怎样说清 Agent 项目中的个人贡献

把项目的“我们”成果与“我”的直接责任分开，用“定义契约、实现链路、建立评测、定位故障、推动决策”这类动词配具体产物和验收证据。同时说明协作者、接口边界和未由自己实现的部分。

### 面试官问“这是你做的吗”怎样回答

直接分层：“项目是团队完成的；我直接负责 A 和 B，C 由另一同事实现，但我与他共同定义了接口或验收。”然后回到自己能提供证据的设计、代码、测试或数据。

## 技术决策的四步表达

1. **约束**：当时必须满足什么，包括数据、时间、团队和现有系统。
2. **候选**：真正比较过哪些方案，至少给出一个合理替代。
3. **决策**：为什么当时选择这个方案，接受了什么代价。
4. **验证**：用什么数据、测试或运行结果证明选择成立，哪些尚未验证。

不要倒果为因地说“因为它最好所以选它”。如果当时没有比较某方案，应说“当时没有做这个对照，现在看它是一个可验证的替代”，而不是虚构调研过程。

## 指标和数字

每个数字都需要口径：测量对象、样本数、时间窗、基线、评分方式和是离线还是线上。“准确率提升 20%”可能是从 50% 到 70% 的 20 个百分点，也可能是从 50% 到 60% 的相对 20%，必须说清。

如果没有可靠数字，可用可验证事实：消除某类重复操作，建立某组回归集，故障从无法复现变为可通过 Trace 定位，或将原来人工步骤转成可审批流程。但也要说明尚未测量的部分。

### 如果没有上线指标怎么回答

如实说当时处于原型、内测或未埋点阶段，介绍已有的离线题集、测试或用户反馈，再给出如果上线会补的指标和实验。要分清“已测得”与“计划测量”。

## 故障复盘的六部分

1. 用户或系统看到了什么影响，影响范围和时间多大。
2. 怎样发现，为什么没有更早发现。
3. 直接触发与根因分别是什么。
4. 当时如何止损、回滚、降级或恢复。
5. 怎样修复并验证，增加了什么回归、监控或约束。
6. 还剩什么风险，如果再做一次会改什么。

根因不应停在“模型不稳定”或“工程师疏忽”。继续追问为什么系统允许该错误影响用户：是缺少校验、越权、无幂等、无回归、无发布门禁还是观测缺失。

## 回答“为什么不用更简单的方案”

先承认复杂度成本，然后说明当时哪个约束让简单方案不足，以及是怎样用数据或故障证明的。例如从单 Agent 拆多 Agent，应有工具过载、权限隔离或可并行收益证据，不是因为多 Agent 更新。

如果简单方案其实已经足够，应直接说会简化。展示能删掉不必要的向量库、队列、多 Agent 或微调，比为所有技术辩护更能体现判断力。

## 面对不知道的追问

先明确已知边界：“这个细节我没有实际验证过。”然后从约束推理：列出需要确认的信息、两个候选方案、风险和最小验证实验。这不是回避，而是展示如何在不完全信息下进行工程决策。

不要用大量相关名词掩盖没有答案，也不要把通用知识说成自己的项目细节。面试官通常会继续追问配置、日志、错误和测试，虚构很快会失去一致性。

## 常见失败场景

- 项目开场五分钟都在讲背景，不说系统与自己责任。
- 用框架名和组件数量替代主链路与决策理由。
- 所有成果都说“提升很大”，数字没有口径或基线。
- 只讲成功结果，说不出一个真实失败、取舍和未解决边界。
- 把团队设计和他人代码都改写为第一人称。
- 遇到未做过的问题时即兴编造配置、故障和指标。

## 生产面试准备检查表

每个项目有一分钟开场；能画一条主链路；列出自己与团队边界；准备两个有候选方案的技术决策；每个指标有口径与基线；准备一个完整故障复盘；知道现有系统的边界；区分已做、已评估、推测与建议；可以说出如果重做会简化或改变什么。

## 20 秒口述

项目回答我会先说用户问题、可验证目标和主链路，再明确我直接负责的部分。关键决策按约束、候选、取舍和验证来讲，指标说清样本、基线和口径。没做过或没测过的内容会明确标记为假设或后续方案。

## 1 至 2 分钟展开

我会用一分钟先建立项目全局：目标用户、原始痛点、主链路、我的责任和一个有口径的结果。面试官追架构时，我按一次真实请求从输入、Context、模型、工具到验证来讲，再补状态恢复与安全。追技术选型时，我说当时约束、真正比较的候选、接受的代价和验证证据。追问失败时，我区分影响、触发、根因、止损、长期修复和剩余风险。整个过程不把团队工作换成个人成果，也不将后来想到的方案伪装成当时已落地。

## 高频追问

### 你在项目中最大的技术取舍是什么

选一个确实有两个合理候选的决策。先说约束，再说为什么选 A 没选 B，明确 A 的代价和何种条件下会改选 B，最后给出当时验证。如果没有真实例子，不用通用方案伪造。

### 如果重做一次你会改什么

选一个与真实边界相关的改进，说明当时为什么没做、现在有什么新证据、改动风险和验证方法。好答案可以是减少复杂度，不一定是增加新技术。

## 系统设计练习

为自己的每个真实项目建立一张事实表：用户与问题、时间与规模、主链路、个人责任、两个技术决策、一个故障、可证明指标、未验证项和当前边界。口述后逐句检查哪些是事实、推断、计划或通用知识。
