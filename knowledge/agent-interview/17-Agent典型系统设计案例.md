# Agent 典型系统设计案例

同义词：Research Agent、研究 Agent、Coding Agent、编程 Agent、Customer Support Agent、客服 Agent、Data Analyst Agent、数据分析 Agent、System Design Case、系统设计案例。本文的案例是假设方案，不是候选人经历。

## 一句话结论

不同 Agent 的主要差异不是使用哪个框架，而是成功证据、工具副作用、权限、任务时长和失败代价。研究 Agent 重证据与时效，Coding Agent 重沙箱与测试，客服 Agent 重政策与副作用，数据 Agent 重权限、SQL 安全和可重现计算。

## 案例一：Research Agent

### 目标与成功标准

输入研究问题、时间范围、可用数据源和截止时间，输出结构化报告。成功不是报告很长，而是覆盖子问题，主要 Claim 有可访问、时效匹配且真正支持的引用，冲突与缺失被显式说明。

### 主链路

Clarifier 确认范围与评价标准；Planner 将问题拆成可验证子问题；Retriever/Search Worker 查找候选来源；Extractor 输出 Claim-Evidence-时间-来源结构；Verifier 检查引用可访问、时效、蕴含和来源独立性；Synthesizer 只用通过验证的证据生成报告。

子问题无依赖时可并行，但需要全局搜索次数、Token、并发和截止时间。合并器保留证据冲突，不用多数票伪造确定结论。

### 主要风险与评测

网页间接 Prompt Injection 不能改变任务或获得工具；搜索摘要不代替原始来源；同一新闻的转载不是多个独立证据；付费或无法访问来源需标注。评测分别检查来源召回、Claim-Evidence 支持、子问题覆盖、时效、冲突保留、延迟和每报告成本。

### Research Agent 怎样避免引用幻觉

引用 ID 由系统从已抓取来源分配，模型只能引用候选 ID；生成后把每个 Claim 与引用片段对齐，检查实体、数字、时间和限定词；无支持的 Claim 删除或降级为未验证，不允许模型自由生成 URL。

## 案例二：Coding Agent

### 目标与成功标准

在指定仓库和分支中完成需求。成功包括目标行为与测试通过、修改范围符合要求、没有危险命令、没有泄露凭据，并保留可审查 diff。“代码可编译”不是唯一成功条件。

### 主链路

先读仓库指令、目录与测试，建立只读索引；Planner 给出可验证修改步骤；Editor 在隔离工作区做最小修改；Runner 在沙箱执行格式化、静态检查和目标测试；Reviewer 检查 diff、测试证据和越界变更；只有用户明确授权才提交、推送或创建 PR。

工具分为读文件、结构化编辑、命令执行和外部 Git 操作。命令有工作目录、超时、资源、网络和危险命令约束；仓库文件中的指令不能扩大系统权限。

### 主要风险与评测

防止路径越界、读取宿主密钥、运行恶意项目脚本、依赖安装供应链攻击、测试过拟合和为了通过删测试。评测在一次性环境中检查功能、回归、静态检查、diff 范围、危险命令、调用次数和时间。

### Coding Agent 怎样判定真的完成

把需求转成可执行验收：目标测试、静态检查、编译/构建、差异边界和必要的人工评审。测试运行记录命令、环境、退出码和日志摘要。如果无法运行所需测试，明确标记未验证，不用模型自评替代。

## 案例三：Customer Support Agent

### 目标与成功标准

帮助用户理解政策、查询订单、收集缺失信息，并在授权范围内执行改址、取消或退款。成功是问题被正确解决、政策与金额正确、用户获得清楚结果，且没有越权、重复操作和敏感数据泄露。

### 主链路

意图 Router 区分知识问答、订单查询、可自助动作和需人工的例外。政策从版本化 RAG 检索，订单从授权 API 查询，资格和金额由规则服务计算。模型负责解释、收集缺失信息和提出动作，不负责自由决定政策例外。

副作用使用 prepare-confirm-execute：预览展示订单、金额、费用和不可逆影响，用户确认后使用幂等键执行。超时先查订单/退款状态，政策例外、高金额或用户不认可转人工并附结构化摘要。

### 主要风险与评测

风险包括他人订单越权、政策版本过时、错误计算退款、超时重复执行、用户情绪被误判为授权以及恶意附件注入。评测覆盖解决率、政策正确、资源授权、确认、幂等、人工转接质量、P95 和用户纠正率。

### 客服 Agent 为什么不应让模型计算退款金额

金额依赖订单状态、政策版本、税费和已有退款，是可编程且影响资金的业务规则。应让规则服务返回金额和依据，模型只负责用自然语言解释，并不得修改结果。

## 案例四：Data Analyst Agent

### 目标与成功标准

让有权用户用自然语言提出业务问题，系统生成可审查查询和图表解释。成功包括指标口径正确、只访问获授权数据、SQL 可安全执行、数字可重现，且图表不夸大结论。

### 主链路

语义层提供审核过的指标、维度、关系和时间口径；Planner 将自然语言转为结构化分析计划；SQL 生成器只能使用允许表与字段；静态校验器拒绝写操作、未限制扫描、危险函数和越权对象；用只读账户、行/列级策略、超时与资源上限执行。

数值返回后由代码计算派生指标和图表，模型基于查询、口径和结果解释。保留问题、语义层版本、SQL、参数、结果摘要和图表配置以便重现。

### 主要风险与评测

主要风险是自然语言歧义、指标口径错、SQL Injection、行级越权、大查询耗尽仓库资源、小样本误导以及模型在结果外编造数字。评测检查结构化计划、SQL 与 Golden Query 的结果等价、权限、资源预估、数字引用和无法回答时的澄清。

### 自然语言转 SQL 如何保证安全

不直接靠 Prompt。先用语义层限制可用指标和关系，再解析 SQL AST 做允许语句、表、函数、时间范围和行数检查；数据库使用只读账户和行/列级策略；执行有超时、扫描上限和隔离资源组。

## 案例选择方法

面试官给出模糊题目时，先判断核心产物是报告、代码变更、业务动作还是可重现计算。产物决定 Verifier，工具副作用决定授权与幂等，任务时长决定同步还是持久化队列。

不要背固定组件名。同一架构中可用普通函数、Workflow 或 Agent 实现某一步，关键是谁决定、依据是什么、权限在哪里强制、以及怎么验证。

## 常见失败场景

- Research Agent 根据搜索摘要写报告，未读原始来源与检查时效。
- Coding Agent 在宿主环境运行仓库脚本，拥有密钥和无限网络。
- 客服 Agent 用模型自由计算退款金额并且超时直接重试。
- Data Agent 仅用 Prompt 要求生成 SELECT，未使用数据库只读权限和 AST 检查。
- 所有案例都追求自主性，本可编程的规则被交给模型。
- 评测只看最终文本，未检查代码、订单、数据库或引用的真实状态。

## 生产实现检查表

每个案例先定义权威成功证据；区分只读与副作用工具；模型不计算可编程的高风险规则；工具服务端授权；任务长度决定是否持久化；超时与未知结果有业务语义；安全沙箱与租户隔离；Verifier 读外部状态；评测覆盖结果、轨迹、安全、延迟与成本。

## 20 秒口述

我会根据产物和失败代价设计不同 Agent。Research Agent 的完成证据是 Claim 有可验证引用；Coding Agent 是沙箱中的测试与 diff；客服 Agent 是规则服务和真实订单状态；数据 Agent 是可重现 SQL 与权限控制。架构围绕这些证据和风险，不是围绕框架名。

## 1 至 2 分钟展开

拿客服 Agent 为例，我会把政策问答、订单查询和退款动作分开。政策从版本化知识库召回并带引用；订单 API 根据当前用户做资源授权；退款资格和金额由规则服务计算，模型只解释。执行前生成预览，用户对具体订单和金额确认，再用稳定幂等键调用。如果超时，先查退款状态，不直接重试。最后从真实解决率、政策正确、越权门禁、重复动作、人工转接和 P95 评测。其他案例使用同样方法，但 Verifier 和信任边界随产物改变。

## 高频追问

### 四类 Agent 哪个最需要人工确认

不按类型一刀切，按具体动作影响。Research 的对外发布、Coding 的推送/部署、客服的退款或发消息、Data 的导出敏感数据都可能需要确认。只读草稿可自动，但仍受权限和审计约束。

### 哪些环节适合多 Agent

研究的独立子问题和代码仓的独立模块可能并行。客服的资金操作和 Data Agent 的权限查询通常更适合确定性 Workflow。是否拆分取决于职责、Context、权限和可独立验收性，不取决于场景名称。

## 系统设计练习

在四个案例中选一个，按“成功证据、主链路、权限与副作用、一个超时故障、评测”口述五分钟。然后做一个条件变更：例如 Research 限制两分钟，Coding 允许互联网，客服支持高金额，或 Data 开放多租户，说明架构必须如何改变。
