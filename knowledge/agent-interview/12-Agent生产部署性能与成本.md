# Agent 生产部署性能与成本

同义词：Production Agent、Deployment、部署、Latency、延迟、Throughput、吞吐、Queue、队列、Backpressure、背压、Rate Limit、限流、Caching、缓存、Cost Optimization、成本优化。本文是通用技术资料。

## 一句话结论

生产 Agent 的性能不是单次模型速度，而是排队、多轮模型、检索、工具、重试和流式输出的端到端结果。应先设定 SLO 和全局预算，再用并行、缓存、模型路由和降级优化，同时保证超载时有背压而不是无限排队。

## 先定义任务级 SLO

交互式 Agent 关心首个有用反馈和端到端完成时间；后台研究 Agent 更关心截止时间内的成功率和每任务成本。把任务分成快速、标准和长任务等级，分别规定延迟、质量、工具和费用预算。

多轮 Agent 每步的小延迟会累加，重试还会放大长尾。报告分位数而不只是平均，并把队列等待、模型首 Token、生成、工具与存储时间分解。

## 同步交互与异步任务

能在一个短截止时间内完成的任务可保持请求内执行并流式反馈。需要长时间工具、并行研究或人工审批的任务进持久化队列，立即返回任务 ID，由状态机展示排队、运行、等待、部分完成、失败和取消。

队列交付通常是至少一次，Worker 必须幂等。消费者心跳或租约超时可以让任务重新可见，但不代表前一 Worker 已停止；结果提交要检查任务版本和幂等键。

## 并行与关键路径

只并行无依赖和无写冲突的工作。对多源检索或独立子任务，并行能缩短关键路径；对计划-执行-验证的强依赖链，强行并行只会浪费成本。

并发必须受全局信号量、每租户限额和下游容量限制。不要让每个请求都并行启动大量子 Agent，否则局部延迟优化会变成系统超载。

## 背压、限流和公平性

当输入速度高于服务能力时，必须减慢或拒绝新工作，不能无限增长内存队列。使用有界队列、每租户令牌桶、任务优先级、并发上限和截止时间，并向用户返回可解释的排队或过载状态。

公平性需要防止一个长任务或大租户占满所有 Worker。可按租户和任务类型分队列或配额，对长任务分段并允许安全检查点。

### 为什么不能只加 Worker 解决积压

瓶颈可能在模型限额、数据库连接、第三方 API 或全局费用预算。盲目加 Worker 只会增加并发重试和下游压力。先用排队时间、资源利用率和各 Span 延迟找真实限制，再扩容或降低单任务工作量。

## 超时、重试与断路器

每个下游调用有截止时间，上游向下传递剩余时间。重试只针对明确瞬时且幂等的错误，使用指数退避和抖动，并有总尝试预算。多层都重试会产生乘法放大，应选择一个最懂业务语义的层负责。

断路器在下游持续失败时快速拒绝，给系统恢复时间。它不替代超时和限流，也不应将业务拒绝统计为基础设施故障。

## 缓存与 Singleflight

适合缓存的内容包括稳定文档解析、Embedding、授权不敏感的公共检索和确定性工具结果。缓存键需包含模型、Prompt、输入、数据版本和权限范围；对个性化或敏感内容不得跨用户共享。

Singleflight 合并同一时刻的相同请求，防止缓存击穿。它不是长期缓存；领导请求取消时要定义跟随者是否仍需要结果，不能无条件取消共享工作。

## 模型路由与降级

使用任务难度、风险、上下文长度和所需能力路由模型，不要只按用户问题长度判断。路由策略需用真实任务集测量错误分布，不同模型的工具 Schema、上下文和输出兼容性也要验证。

降级应显式：缩小搜索源、停止非必要反思、使用部分结果、延后完整报告或转人工。降级不能悄悄用弱模型执行高风险决策，也不能在缺少证据时伪装完整。

## 成本模型

每任务成本至少包括输入与输出 Token、Embedding、重排、工具 API、计算、存储和观测。更有意义的是“每个成功任务成本”，因为便宜但失败的请求不创造价值。

优化顺序是先减少无用步骤和上下文，再缓存稳定工作，对合适子任务使用较小模型，最后才调整生成长度或价格。每次优化都要检查成功率、安全和长尾延迟，防止只看总 Token 下降。

## 发布与容量规划

发布前用目标并发、上下文长度和工具延迟做负载测试，但模型供应商限额和外部 API 需用隔离或合成流量，不能因压测产生真实副作用。容量模型使用到达率、平均执行时间、并行度、重试系数和峰值余量。

新模型或 Prompt 先离线评测，再 Shadow、Canary 和逐步放量。发布需要一键回滚模型路由、Prompt 和工具 Schema，不把多个不可分离变更一次全量推出。

## 常见失败场景

- 只优化模型生成时间，队列与工具长尾仍占大部分。
- 没有有界队列，流量突发后所有请求一起超时和重试。
- API、工具适配层和 Worker 都重试，失败流量被乘法放大。
- 缓存键缺少租户或权限维度，用户间数据串扰。
- 异步任务重复交付，非幂等 Worker 产生两次副作用。
- 为降低价格用小模型处理高风险任务，但没有独立验证。

## 生产实现检查表

任务类型有延迟、质量和费用 SLO；分解队列、模型和工具延迟；长任务持久化且 Worker 幂等；并行受全局与租户限额；队列有界并支持背压；截止时间向下传递；重试只在一层且带抖动；缓存包含版本和权限维度；模型路由经评测；监测每成功任务成本；发布使用 Canary 且可回滚。

## 20 秒口述

我先为不同 Agent 任务定义延迟、质量和成本 SLO，再分解队列、模型和工具的关键路径。长任务进持久化队列，Worker 幂等；系统用有界队列、租户限额和背压保护下游。优化看每成功任务成本，不只看 Token 单价。

## 1 至 2 分钟展开

我会先区分交互式与后台任务，为它们设定首个有用结果、P95 完成时间、成功率和单任务费用目标。然后用 Trace 找关键路径：无依赖检索可并行，长任务进队列并保存检查点。并发通过全局信号量和租户限额控制，超载时明确排队或拒绝。每个调用有剩余截止时间，重试只在一个理解业务的层进行。最后用缓存、模型路由和显式降级优化，但任何节省都要重新检查质量和安全。

## 高频追问

### 怎样降低 Agent 延迟

先用 Trace 分解等待、首 Token、生成、检索和工具；减少不必要轮次与 Context；并行无依赖工作；流式返回真正有用的中间结果；缓存稳定工作；按任务难度路由模型；对非必要反思和评审做消融。

### 流式输出会让任务更快吗

它主要改善感知延迟，不一定缩短总完成时间。应只流式用户可理解且不会被后续验证推翻的内容，不要在工具和安全检查前展示未确认的“已完成”。

## 系统设计练习

设计研究 Agent 任务平台：API 写入任务状态并返回 ID；按租户公平排队；Orchestrator 按依赖图为 Worker 分配预算；无依赖搜索并行；每步保存检查点；提供商限流时背压而不是无限重试；超过截止时间返回带来源的部分结果；监测每成功报告成本和 P95。
